# Звук в шаринге экрана

**Задача:** при шаринге экрана в групповом звонке слушатели должны слышать звук компьютера шарящего (источник — устройство вывода по умолчанию). Захват включается автоматически при каждом старте шаринга, без отдельного тумблера в UI.

**Дата:** 2026-07-23
**Ветка:** `VYC-45-sound-in-sharing`

## Проблема

Экран-шеринг (SFU, групповые звонки) уже реализован (`groupCall.ts`, `GroupCallUI.tsx`), но и в Electron-пути (`desktopCapturer` + mandatory constraints), и в браузерном (`getDisplayMedia`) звук явно отключён (`audio: false`). Слушатели видят видео, но не слышат звук воспроизводимого видео/музыки/игры на компьютере шарящего.

P2P-звонки (`call.ts`) шаринга экрана не имеют вообще — задача только про групповые звонки (SFU).

## Архитектурное решение

У каждого участника в SFU жёстко **один recvonly audio-transceiver**, создаваемый один раз при входе в комнату (см. `project_sfu_internals`), и он не переоткрывается в течение звонка. Добавление второго независимого аудиопотока «звук шаринга» потребовало бы динамического второго аудио-трансивера на SFU, нового типа сигналинг-сообщения и правок в `participant_session.go`/track routing — самом багоопасном коде проекта (в бордe отдельно отмечен как «самый сложный и багоопасный»).

Вместо этого — **чисто клиентское решение**: подмешать звук компьютера в уже существующий исходящий аудиотрек через Web Audio API, в ту же цепочку, где сейчас живёт шумоподавление (`noiseCancellation.ts`):

```
mic ──► source ──► [NC worklet / bypass] ──► micGain ──► destination ──► (тот же sender-трек)
                                                              ▲
system audio (getDisplayMedia/desktop loopback) ─────────────┘
```

SFU, сигналинг-протокол и любой серверный (Go) код не меняются вообще.

Так как это тот же самый исходящий трек, что уже переживает авто-реконнект (VYC-24) без специального кода, звук шаринга автоматически наследует эту устойчивость — никакой логики восстановления после reconnect не требуется (в отличие от видео шаринга, для которого уже есть `pendingScreenRestore`/`applyScreenRestore`).

## Компоненты и изменения

### `noiseCancellation.ts`

- В `AudioChain` добавляется постоянная нода `micGain: GainNode`, вставленная между веткой микрофона (bypass или NC-worklet) и `destination`. И `activateChain`, и `wireBypass` теперь подключают свой выходной узел к `micGain`, а `micGain` подключается к `destination` один раз при создании цепочки в `doCreateChain`.
- Мьют микрофона переезжает на этот gain (0 = замьючен, 1 = нет) вместо `track.enabled` на выходном треке — чтобы мьют микрофона не глушил заодно и звук шаринга, который сидит в том же треке.
- Новый метод `setMicMuted(streamId: string, muted: boolean): boolean` — если цепочка для `streamId` найдена, выставляет `micGain.gain.value` и возвращает `true`. Если цепочки нет (например, `NoiseCancellationService.isSupported()` вернул `false` и `doCreateChain` не создавал цепочку), возвращает `false` — вызывающий код должен откатиться на старое поведение (`track.enabled`), чтобы мьют продолжал работать и без NC.
- Новый метод `attachExtraAudio(streamId: string, stream: MediaStream): (() => void) | null` — создаёт `MediaStreamAudioSourceNode` из переданного потока и подключает его **напрямую к `destination`**, в обход `micGain` и NC-worklet'а (шумодав не должен трогать звук с рабочего стола, а мьют микрофона не должен его глушить). Возвращает функцию отключения (`source.disconnect()`). Возвращает `null`, если цепочки для `streamId` нет — тогда звук шаринга просто не подмешивается, видео идёт как раньше.

### `groupCall.ts`

- Новое приватное поле `screenAudioDetach: (() => void) | null = null`.
- `startScreenShare(sourceId?, quality)`:
  - **Electron-путь** (есть `sourceId`): к mandatory-констрейнтам добавляется `audio: { mandatory: { chromeMediaSource: 'desktop', chromeMediaSourceId: sourceId } }`, но весь `getUserMedia`-вызов оборачивается в `try { video+audio } catch { video-only как сейчас }`. Это обязательно: mandatory-констрейнты в Chromium валят **весь** запрос при неподдерживаемом сочетании (например, шаринг конкретного окна вместо всего экрана, или платформа без loopback-захвата, как Linux) — без fallback это сломало бы существующий работающий шаринг видео на таких платформах/источниках.
  - **Браузерный путь** (`getDisplayMedia`): `audio: false` → `audio: true`. По спецификации при отсутствии поддержки браузер просто не даёт аудиотрек, исключения не бросает — отдельный try/catch не нужен.
  - После получения `stream`: если есть `stream.getAudioTracks()[0]` и есть `this.localStream` (микрофон был доступен при входе в комнату → есть NC-цепочка) — вызывается `noiseCancellationService.attachExtraAudio(this.localStream.id, new MediaStream([audioTrack]))`, результат сохраняется в `screenAudioDetach`.
  - Если аудиотрека нет, либо `attachExtraAudio` вернул `null` (нет NC-цепочки — узкий случай входа в звонок без микрофона), — звук просто не подмешивается, видео шарится как сегодня. Никакой ошибки пользователю не показывается.
- `stopScreenShare()`: перед остановкой треков вызывает `this.screenAudioDetach?.()` и обнуляет поле.
- `teardown()`: то же самое (`screenAudioDetach?.()` + обнуление) — на случай выхода из звонка прямо во время шаринга (путь через `leaveGroupCall` → `teardown()` напрямую, минуя `stopScreenShare`).
- `toggleMuteAudio()`: вместо `t.enabled = ...` вызывает `noiseCancellationService.setMicMuted(this.localStream.id, muted)`. Если метод вернул `false` (цепочки нет), откатывается на прежний `t.enabled = !muted` — сохраняя сегодняшнее поведение для этого редкого случая.

### UI (`GroupCallUI.tsx`) и Electron (`main.ts`/`preload.ts`)

Без изменений. Захват звука включается автоматически при каждом старте шаринга, новый тумблер не нужен (решено на этапе брейнсторминга). Разрешение `media` в Electron уже выдаётся автоматически (`setPermissionRequestHandler`), IPC/`desktopCapturer` трогать не требуется.

## Поведение по платформам (best-effort, без ошибок пользователю)

| Платформа/сценарий | Результат |
|---|---|
| Electron + Windows, шарим весь экран | Звук системы захватывается и передаётся |
| Electron + macOS 13+, шарим весь экран | Как правило работает (ScreenCaptureKit) |
| Electron + Linux | Обычно недоступно → тихий fallback на video-only |
| Шарим конкретное окно (любая ОС) | Часто недоступно → тихий fallback |
| Браузер (не Electron), Windows/ChromeOS | Работает через нативный чекбокс "share audio" в пикере ОС |
| Браузер, Linux/прочее | Как правило недоступно → трек просто без звука |
| Пользователь без микрофона при входе в звонок | Звук шаринга не подмешивается, видео шарится как обычно |

## Edge cases

- Повторный старт шаринга (`startScreenShare` вызывается, пока уже идёт другой шаринг) — существующий код сам вызывает `stopScreenShare()` в начале, которая уже отключит предыдущий `screenAudioDetach`; новый цикл создаст свой.
- Реконнект во время шаринга со звуком — `partialTeardown()` не трогает ни `screenStream`, ни `localStream`, ни NC-цепочку, поэтому и видео (через существующий `pendingScreenRestore`), и подмешанный звук (трек/нода не пересоздаются) переживают реконнект без дополнительного кода.
- Переключение NC (шумоподавление) вкл/выкл во время шаринга — `activateChain`/`wireBypass` переподключают только `chain.source`/`stage.node` к `micGain`, не трогая ноду системного звука, подключённую напрямую к `destination`.
- Мьют микрофона во время шаринга со звуком — слушатели продолжают слышать звук шаринга, голос пропадает (проверено дизайн-решением на этапе брейнсторминга).

## Тестирование

Изменение затрагивает только клиент, серверный код и WS/SFU-протокол не меняются — юнит-тестов на Go-стороне не требуется.

Ручной QA (Electron-сборка на Linux — доступная среда):
- шаринг экрана по-прежнему стартует и показывает видео, если аудиотрек захватить не удалось (video-only fallback реально срабатывает, а не валит весь `startScreenShare` с ошибкой);
- если есть доступ к Windows/macOS — проверить, что звук реально доходит до слушателя;
- мьют микрофона во время шаринга со звуком не гасит звук шаринга у слушателя;
- остановка и повторный запуск шаринга работают штатно (нет утечек `AudioNode`, звук не дублируется);
- выход из звонка прямо во время шаринга со звуком не оставляет висящих подключённых audio-нод (проверяется по отсутствию ошибок в консоли/логах `gcLog`).

Regression: существующий `client/e2e/run.sh` (сценарий шаринга без камеры) должен продолжать проходить без изменений — он не касается аудио, но подтверждает, что видео-путь шаринга остался рабочим.

## Вне скоупа

- Отдельная громкость/мьют звука шаринга независимо от общей громкости участника — общая громкость участника (`VolumeControlPopover`) и так применяется ко всему смешанному треку.
- UI-тумблер «делиться звуком» — решено, что захват всегда автоматический.
- Явное сообщение пользователю о том, что звук шаринга недоступен на его платформе — решено тихо деградировать до video-only.
- P2P-звонки (`call.ts`) — там шаринга экрана нет вообще, не в скоупе этой задачи.
- Раздельные аудиодорожки на SFU (второй transceiver) — сознательно отвергнутый вариант из-за риска для самого нестабильного участка кодовой базы.
