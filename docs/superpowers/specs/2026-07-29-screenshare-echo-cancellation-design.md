# Исключить звук звонка из аудио при демонстрации экрана

**Дата:** 2026-07-29
**Ветка:** `screenshare-echo-cancellation` (создаётся при реализации)
**Область:** только клиент, только групповой звонок (`services/groupCall.ts`, `services/noiseCancellation.ts`, новый `services/echoCancellation.ts` + новые AudioWorklet-файлы). SFU, WS-сигналинг и любой серверный (Go) код не меняются.

## Проблема

Звук шаринга экрана (`docs/superpowers/specs/2026-07-23-screenshare-audio-design.md`, VYC-45) захватывается как OS-level loopback всего звукового вывода машины (`chromeMediaSource: 'desktop'` в Electron, либо `getDisplayMedia({audio: true})` в браузере) и подмешивается через Web Audio (`noiseCancellationService.attachExtraAudio`) прямо в исходящий трек звонка (`groupCall.ts:611-620`).

Голоса других участников звонка воспроизводятся локально через обычный `<video>`-элемент (`el.srcObject = stream; el.play()`, `GroupCallUI.tsx:75-101`) — то есть реально звучат из динамиков. OS-level loopback не различает источники и захватывает весь микс, включая эти голоса. В результате: A шарит экран со звуком → loopback захватывает голос B, который играет у A из динамиков → подмешивается в исходящий трек A → B слышит свой же голос обратно (и голоса прочих участников — дублированно).

Технического способа сказать loopback-захвату «исключи звук именно этого приложения» кроссплатформенно нет (нативные API есть только на конкретных ОС — Windows Process-Loopback-Exclude, macOS `excludesCurrentProcessAudio` — но ни то ни другое не проброшено в JS через Electron/Chromium). Аудиодорожка при шаринге вообще доступна только при шаринге **целого экрана** (не отдельного окна), так что и вариант «захватывать звук только демонстрируемого окна» не применим — эта дорожка в принципе не появляется для window-источников.

Значит единственный технически корректный путь убрать именно голоса звонка, сохранив остальной системный звук — адаптивное подавление эха (AEC): вычесть из захваченного системного потока то, что коррелирует с уже известным сигналом звонка (мы точно знаем, что рендерим — это те же самые удалённые аудиотреки).

## Архитектурное решение

Клиентское решение, встраивается в существующую cepочку системного звука (VYC-45), ничего в её внешнем контракте не меняя:

```
mic ──► NC chain ──► destination ──► sender               (не меняется)

remote participants' audio ──► referenceBus                (новое; живёт, пока активен шаринг со звуком)

system loopback ──► AEC(worklet, ref=referenceBus) ──► cleaned track ──► attachExtraAudio ──► destination
```

`referenceBus` — постоянно обновляемая сумма аудиотреков всех текущих удалённых участников звонка (то же самое, что физически звучит из динамиков пользователя). AEC-воркер вычитает из захваченного loopback-сигнала то, что коррелирует с этим референсом, и отдаёт очищенный трек — который дальше идёт в `attachExtraAudio` точно так же, как сегодня идёт сырой `systemAudioTrack`.

### Алгоритм (v1)

1. Грубая оценка задержки между `referenceBus` и захваченным сигналом периодической кросс-корреляцией по огибающей (обновляется раз в несколько сотен мс, диапазон оценки ограничен разумными пределами).
2. NLMS-адаптивный фильтр поверх выровненного по задержке референса — вычитает предсказанную эхо-составляющую из захваченного сигнала.
3. Пустой `referenceBus` (никого нет в звонке / все замьючены) → фильтру нечего подавлять, трек проходит как есть.

Ожидаемое качество: заметно подавляет дублирование голосов звонка, но не дотягивает до промышленных AEC3-реализаций — возможны слабые остатки эха при резко меняющейся задержке или нескольких одновременных говорящих. Это принятое ограничение v1 (подтверждено на этапе брейнсторминга), не считается багом.

Звуки самого приложения (join/leave-чирпы, VYC-49) в `referenceBus` не включаются — короткие и редкие, не входят в критерии приёмки задачи, риск остаточного дублирования незначителен.

## Компоненты и изменения

### Новое: `client/src/audio-worklets/echoCancellationCore.js`

Чистый ES-модуль с самим алгоритмом (NLMS + оценка задержки). Работает с `Float32Array`-фреймами на вход/выход, без обращений к Web Audio API — тестируется напрямую в Node (`tsx`), без DOM/AudioContext.

### Новое: `client/src/audio-worklets/EchoCancellationWorklet.js`

`AudioWorkletProcessor`-обёртка: два входа (`referenceBus`, захваченный системный трек), импортирует и гоняет `echoCancellationCore.js` на реальных аудиофреймах, отдаёт очищенный выход. Копируется в `public/audio/` тем же механизмом, что уже копирует `AudioPipelineWorklet.js` (`copy-audio-assets`/аналогичный шаг), грузится через `context.audioWorklet.addModule(...)` — тот же паттерн, что уже использует NC (`noiseCancellation.ts:408`).

### Новое: `client/src/services/echoCancellation.ts`

- Держит `referenceBus`: отдельный `AudioContext` + `MediaStreamAudioDestinationNode`, куда подключаются аудиотреки текущих удалённых участников.
- `attachEchoCancellation(capturedAudioTrack: MediaStreamTrack): { track: MediaStreamTrack; detach: () => void } | null` — создаёт `AudioWorkletNode`, коннектит `referenceBus` и захваченный трек как два входа, возвращает очищенный `MediaStreamTrack`. При ошибке инициализации воркера (`addModule`/конструктор ноды бросили) — возвращает `null`, нефатально.

### `groupCall.ts`

- `startScreenShare()`: `referenceBus` заполняется из `this.remoteStreams` (уже существующая карта). Захваченный `systemAudioTrack` прогоняется через `echoCancellationService.attachEchoCancellation(...)`; если вернулся очищенный трек — он идёт в `noiseCancellationService.attachExtraAudio(...)` вместо сырого; если `attachEchoCancellation` вернул `null` (воркер не поднялся) — используется сырой трек как раньше (текущее поведение VYC-45, без регрессии).
- `stopScreenShare()` и `teardown()`: помимо текущего `screenAudioDetach?.()`, вызывается teardown AEC-ноды и разбор `referenceBus`.
- `pc.ontrack`: пока активен шаринг со звуком — подключать источник для нового удалённого аудиотрека в `referenceBus` (симметрично уже существующему добавлению в `this.remoteStreams`).
- Ветка `case 'participant_left'`: пока активен шаринг со звуком — отключать источник ушедшего участника от `referenceBus` (симметрично `this.remoteStreams.delete(user_id)`).

### `noiseCancellationService`

Без изменений контракта — `attachExtraAudio` как и раньше просто получает `MediaStream`, не знает и не должен знать про AEC.

## Edge cases

- Шаринг экрана без звука (аудиотрек не захвачен) — не заходит в новую ветку вообще, поведение не меняется.
- Соло в звонке (никого кроме себя) на момент старта шаринга — `referenceBus` пуст, AEC — no-op passthrough.
- Участник присоединяется/выходит во время активного шаринга со звуком — `referenceBus` обновляется динамически через хуки в `ontrack`/`participant_left`, без перезапуска шаринга.
- Повторный старт шаринга (`startScreenShare` вызывается, пока уже идёт другой шаринг) — существующий код сам вызывает `stopScreenShare()` в начале, которая уже разберёт предыдущий AEC-узел и `referenceBus`; новый цикл создаст свои.
- Реконнект во время шаринга со звуком — не в скоупе новых изменений: `partialTeardown()` не трогает `screenStream`/`localStream`/NC-цепочку сегодня, и новый AEC-узел живёт на том же принципе (не пересоздаётся при реконнекте).
- Ошибка инициализации AEC-воркера (например, `AudioWorklet` не поддерживается) — тихий откат на сырой системный звук (текущее поведение VYC-45), не на отключение звука шаринга целиком.

## Тестирование

Сети/npm-registry нет в текущей среде разработки, тест-раннера (vitest/jest) в проекте не установлено — тестирование в стиле уже существующего `client/e2e/run.sh` (кастомный скрипт, не фреймворк):

- **Синтетический скрипт на `tsx`** для `echoCancellationCore.js` (без браузера/DOM): подаётся известный референс-сигнал + смешанный сигнал (референс со сдвигом/затуханием + независимая «прочая системная» составляющая); проверяется, что после сходимости фильтра референс-коррелированная составляющая заметно подавлена (порог в дБ), а независимая составляющая сохраняет энергию (не давится AEC заодно с эхом). Отдельно — тест на пустой референс (no-op) и на несколько одновременных референс-источников (несколько участников звонка).
- **Новый e2e-сценарий** по образцу `no-camera-screenshare.html`: sharer + viewer + третий участник с синтетическим тоновым аудио (референс); sharer стартует шаринг с синтетическим loopback-звуком = референс-тон + отдельный «системный» тон; проверяется, что viewer получает ослабленный референс-тон и сохранённый системный тон.
- Существующий `npm run test:e2e` (видео-путь шаринга, VYC-22) не трогается — должен продолжать проходить без изменений, подтверждая отсутствие регрессии в видео-пути.
- Ручная проверка на реальном железе (Windows/macOS, если будет доступ) — синтетические тесты валидируют алгоритм на известных сигналах, но не то, как он ведёт себя на настоящем OS-level loopback; это отдельно отмечается как открытый риск, не блокирующий мердж v1.

## Вне скоупа

- Качество уровня промышленных AEC3-реализаций — сознательно принятое ограничение v1.
- Подавление звуков самого приложения (join/leave-чирпы) в захваченном системном звуке.
- Раздельные аудиодорожки на SFU (второй transceiver, чтобы звук шаринга слышали только зрители демонстрации, а не все участники звонка) — по-прежнему сознательно отвергнутый вариант (см. VYC-45 design doc) из-за риска для самого нестабильного участка кодовой базы; не нужен и для этой задачи, т.к. проблема решается на уровне захвата, а не маршрутизации.
- Отдельная громкость/мьют звука шаринга — не меняется.
- P2P-звонки (`call.ts`) — там шаринга экрана нет вообще.
