# Исключить звук звонка из аудио при демонстрации экрана

**Дата:** 2026-07-29
**Ветка:** `screenshare-echo-cancellation` (создаётся при реализации)
**Область:** только клиент, только групповой звонок (`services/groupCall.ts`, `services/noiseCancellation.ts`, новый `services/echoCancellation.ts` + новые worker/worklet-файлы). SFU, WS-сигналинг и любой серверный (Go) код не меняются.

## Проблема

Звук шаринга экрана (`docs/superpowers/specs/2026-07-23-screenshare-audio-design.md`, VYC-45) захватывается как OS-level loopback всего звукового вывода машины (`chromeMediaSource: 'desktop'` в Electron, либо `getDisplayMedia({audio: true})` в браузере) и подмешивается через Web Audio (`noiseCancellationService.attachExtraAudio`) прямо в исходящий трек звонка (`groupCall.ts:611-620`).

Голоса других участников звонка воспроизводятся локально через обычный `<video>`-элемент (`el.srcObject = stream; el.play()`, `GroupCallUI.tsx:75-101`) — то есть реально звучат из динамиков. OS-level loopback не различает источники и захватывает весь микс, включая эти голоса. В результате: A шарит экран со звуком → loopback захватывает голос B, который играет у A из динамиков → подмешивается в исходящий трек A → B слышит свой же голос обратно (и голоса прочих участников — дублированно).

Технического способа сказать loopback-захвату «исключи звук именно этого приложения» кроссплатформенно нет (нативные API есть только на конкретных ОС — Windows Process-Loopback-Exclude, macOS `excludesCurrentProcessAudio` — но ни то ни другое не проброшено в JS через Electron/Chromium). Аудиодорожка при шаринге вообще доступна только при шаринге **целого экрана** (не отдельного окна), так что и вариант «захватывать звук только демонстрируемого окна» не применим — эта дорожка в принципе не появляется для window-источников.

Значит единственный технически корректный путь убрать именно голоса звонка, сохранив остальной системный звук — адаптивное подавление эха (AEC): вычесть из захваченного системного потока то, что коррелирует с уже известным сигналом звонка (мы точно знаем, что рендерим — это те же самые удалённые аудиотреки).

## Архитектурное решение

Клиентское решение, встраивается в существующую цепочку системного звука (VYC-45), ничего в её внешнем контракте не меняя:

```
mic ──► NC chain ──► destination ──► sender               (не меняется)

remote participants' audio ──► referenceBus                (новое; живёт, пока активен шаринг со звуком)

system loopback ──► AEC(worklet+worker, ref=referenceBus) ──► cleaned track ──► attachExtraAudio ──► destination
```

`referenceBus` — постоянно обновляемая сумма аудиотреков всех текущих удалённых участников звонка (то же самое, что физически звучит из динамиков пользователя). AEC-модуль вычитает из захваченного loopback-сигнала то, что коррелирует с этим референсом, и отдаёт очищенный трек — который дальше идёт в `attachExtraAudio` точно так же, как сегодня идёт сырой `systemAudioTrack`.

### Алгоритм: настоящий WebRTC AEC3 (не самописный)

Изначально рассматривался самописный NLMS-фильтр с собственной оценкой задержки — решение было принято в условиях, когда сеть казалась недоступной. Сеть оказалась просто медленной (не отсутствующей); после проверки найден и провалидирован пакет **`@ennuicastr/webrtcaec3.js`** (npm, BSD-3-Clause, 0 зависимостей, ~170KB wasm + ~260KB JS-обвязка, без pthreads/`SharedArrayBuffer` — не требует специальных заголовков) — WASM-порт настоящей библиотеки WebRTC AEC3 (та же, что использует сам Chrome). Решено использовать её вместо самописного алгоритма: то же самое решение задачи, кардинально выше качество и надёжность (проверенный годами эксплуатации код вместо новой DSP-логики с нуля), меньше площадь для новых багов.

API библиотеки (`dist/webrtcaec3.types.d.ts`):
```js
const AEC3 = await WebRtcAec3();                       // грузит WASM
const aec = new AEC3.AEC3(48000, renderChannels, captureChannels);
aec.analyze(renderFrame);                                // референс (звук звонка)
const outSz = aec.processSize(captureFrame);
aec.process(outBuf, captureFrame);                        // захваченный системный звук → очищенный outBuf
aec.setAudioBufferDelay(ms);                              // опционально; библиотека и так делает встроенную оценку задержки
aec.free();
```
Пример использования (mono self-echo demo) есть в `demo/self-echo-cancel.html` пакета. Sample rate — 48000 (совпадает с `AudioContext({ sampleRate: 48000 })`, который уже используется в `noiseCancellation.ts`).

Библиотека **синхронная** (README прямо рекомендует гонять её в Web Worker) — это ровно тот же паттерн, что уже применяется в проекте для NC (`AudioPipelineWorklet.js` ⇄ `AudioPipelineWorker.js` через `MessageChannel`, батчинг фреймов). Переиспользуем архитектуру, а не изобретаем новую:

- `render`-канал (`referenceBus`) кормит `aec.analyze(...)`;
- `capture`-канал (захваченный системный звук) кормит `aec.process(...)`, результат — очищенный поток.

Пустой `referenceBus` (никого нет в звонке / все замьючены) → `analyze` получает тишину, `process` практически не меняет захваченный сигнал (нечего подавлять).

Звуки самого приложения (join/leave-чирпы, VYC-49) в `referenceBus` не включаются — короткие и редкие, не входят в критерии приёмки задачи, риск остаточного дублирования незначителен.

## Компоненты и изменения

### Новая зависимость

`@ennuicastr/webrtcaec3.js` (`client/package.json`, `devDependencies`/`dependencies`). Файлы `webrtcaec3-*.wasm`/`.js` копируются в `public/audio/` тем же механизмом, что уже копирует `AudioPipelineWorklet.js`/`rnnoise.wasm` (`copy-audio-assets`-скрипт расширяется на новые файлы) — тот же паттерн, что уже использует NC.

### Новое: `client/src/audio-worklets/EchoCancellationWorklet.js`

`AudioWorkletProcessor` с двумя входами (`referenceBus`, захваченный системный трек). Пересылает фреймы в воркер через `MessageChannel` (батчинг, как в `AudioPipelineWorklet.js`), получает обратно очищенные фреймы, отдаёт их на выход ноды. Копируется в `public/audio/`, грузится через `context.audioWorklet.addModule(...)` — тот же вызов, что уже делает NC (`noiseCancellation.ts:408`).

### Новое: `client/src/audio-worklets/EchoCancellationWorker.js`

Web Worker: грузит `WebRtcAec3()`, держит инстанс `AEC3`, на каждый батч фреймов от воркета вызывает `analyze()` (для render) и `process()` (для capture), шлёт очищенные фреймы обратно. Структура — по образцу `AudioPipelineWorker.js`.

### Новое: `client/src/services/echoCancellation.ts`

- Держит `referenceBus`: отдельный `AudioContext` + `MediaStreamAudioDestinationNode`, куда подключаются аудиотреки текущих удалённых участников.
- `attachEchoCancellation(capturedAudioTrack: MediaStreamTrack): Promise<{ track: MediaStreamTrack; detach: () => void } | null>` — поднимает worklet+worker (по аналогии с `buildStage` в `noiseCancellation.ts`), коннектит `referenceBus` и захваченный трек как два входа, возвращает очищенный `MediaStreamTrack`. При ошибке инициализации (`addModule`/загрузка WASM в воркере бросили) — возвращает `null`, нефатально.

### `groupCall.ts`

- `startScreenShare()`: `referenceBus` заполняется из `this.remoteStreams` (уже существующая карта). Захваченный `systemAudioTrack` прогоняется через `echoCancellationService.attachEchoCancellation(...)`; если вернулся очищенный трек — он идёт в `noiseCancellationService.attachExtraAudio(...)` вместо сырого; если `attachEchoCancellation` вернул `null` (воркер/WASM не поднялись) — используется сырой трек как раньше (текущее поведение VYC-45, без регрессии).
- `stopScreenShare()` и `teardown()`: помимо текущего `screenAudioDetach?.()`, вызывается teardown AEC-ноды/воркера (включая `aec.free()`) и разбор `referenceBus`.
- `pc.ontrack`: пока активен шаринг со звуком — подключать источник для нового удалённого аудиотрека в `referenceBus` (симметрично уже существующему добавлению в `this.remoteStreams`).
- Ветка `case 'participant_left'`: пока активен шаринг со звуком — отключать источник ушедшего участника от `referenceBus` (симметрично `this.remoteStreams.delete(user_id)`).

### `noiseCancellationService`

Без изменений контракта — `attachExtraAudio` как и раньше просто получает `MediaStream`, не знает и не должен знать про AEC.

## Edge cases

- Шаринг экрана без звука (аудиотрек не захвачен) — не заходит в новую ветку вообще, поведение не меняется.
- Соло в звонке (никого кроме себя) на момент старта шаринга — `referenceBus` пуст, AEC получает тишину на `analyze`, `process` почти не меняет сигнал.
- Участник присоединяется/выходит во время активного шаринга со звуком — `referenceBus` обновляется динамически через хуки в `ontrack`/`participant_left`, без перезапуска шаринга.
- Повторный старт шаринга (`startScreenShare` вызывается, пока уже идёт другой шаринг) — существующий код сам вызывает `stopScreenShare()` в начале, которая уже разберёт предыдущий AEC-узел/воркер и `referenceBus`; новый цикл создаст свои.
- Реконнект во время шаринга со звуком — не в скоупе новых изменений: `partialTeardown()` не трогает `screenStream`/`localStream`/NC-цепочку сегодня, и новый AEC-узел живёт на том же принципе (не пересоздаётся при реконнекте).
- Ошибка инициализации AEC (например, `AudioWorklet` не поддерживается, либо WASM не загрузился) — тихий откат на сырой системный звук (текущее поведение VYC-45), не на отключение звука шаринга целиком.

## Тестирование

Поскольку сама библиотека AEC3 — проверенный годами код из Chrome, тестировать «работает ли алгоритм эхоподавления» не требуется; тестируем именно **нашу интеграцию** (правильно ли собираются render/capture потоки, не ломается ли существующее поведение):

- **Синтетическая проверка на `tsx`** (тест-раннера в проекте нет — пишем в стиле уже существующего `client/e2e/run.sh`, отдельный скрипт, не фреймворк): загрузить `WebRtcAec3()` в Node (WASM-загрузчик у Emscripten обычно универсален для Node/браузера — если окажется браузеро-only, тест переносится в headless Chrome через e2e-харнесс, а не тест-раннер), подать известный референс-сигнал + смешанный сигнал (референс со сдвигом/затуханием + независимая «прочая системная» составляющая) через `analyze`/`process`, проверить: референс-коррелированная составляющая заметно подавлена, независимая — сохраняет энергию, пустой референс — почти no-op.
- **Новый e2e-сценарий** по образцу `no-camera-screenshare.html`: sharer + viewer + третий участник с синтетическим тоновым аудио (референс); sharer стартует шаринг с синтетическим loopback-звуком = референс-тон + отдельный «системный» тон; проверяется, что viewer получает ослабленный референс-тон и сохранённый системный тон.
- Существующий `npm run test:e2e` (видео-путь шаринга, VYC-22) не трогается — должен продолжать проходить без изменений, подтверждая отсутствие регрессии в видео-пути.
- Ручная проверка на реальном железе (Windows/macOS, если будет доступ) — синтетические тесты валидируют интеграцию на известных сигналах, но не то, как AEC3 ведёт себя на настоящем OS-level loopback с реальной непредсказуемой задержкой; библиотека для этого и создавалась (порт продакшн-кода Chrome), поэтому риск ниже, чем был бы для самописного алгоритма, но живая проверка всё равно желательна и не блокирует мердж.

## Вне скоупа

- Подавление звуков самого приложения (join/leave-чирпы) в захваченном системном звуке.
- Раздельные аудиодорожки на SFU (второй transceiver, чтобы звук шаринга слышали только зрители демонстрации, а не все участники звонка) — по-прежнему сознательно отвергнутый вариант (см. VYC-45 design doc) из-за риска для самого нестабильного участка кодовой базы; не нужен и для этой задачи, т.к. проблема решается на уровне захвата, а не маршрутизации.
- Отдельная громкость/мьют звука шаринга — не меняется.
- P2P-звонки (`call.ts`) — там шаринга экрана нет вообще.
