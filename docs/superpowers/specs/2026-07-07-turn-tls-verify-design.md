# TURN: TLS (turns:5349) и проверка после деплоя

**Дата:** 2026-07-07
**Ветка:** VYC-23-coturn (доработка коммита f8cc982 «Добавил TURN-сервер»)

## Цель

1. Клиенты в сетях, где режется UDP и plain-TCP, но разрешён исходящий TLS,
   должны подключаться к звонкам через `turns:` на порту 5349.
2. После деплоя должен быть воспроизводимый способ убедиться, что TURN
   (все три транспорта) реально работает.

Порт 443 сознательно не используется: на сервере один публичный IP, 443 занят
nginx (api/front), а SNI-мультиплексирование признано неоправданным усложнением
для пет-проекта. Сети «только 80/443» остаются непокрытыми — принятое
ограничение.

## Что не меняется

- Серверный Go-код и клиентский TypeScript: URL-ы TURN приходят клиенту из
  `TURN_URLS` через `GET /api/v1/turn/credentials`, добавление `turns:`-URL —
  чисто конфигурационное изменение.
- Dev-окружение (`docker-compose.yml`, `.env.example`): TURN в dev опционален
  и не поднимается.
- Схема ephemeral-креденшелов (coturn REST API, HMAC-SHA1 от
  `<expiry>:<user-id>`).

## Изменения

### 1. coturn (`docker-compose.prod.yml`)

- Убрать `--no-tls`.
- Добавить: `--tls-listening-port=5349`, `--cert=/certs/fullchain.pem`,
  `--pkey=/certs/privkey.pem`, `--no-tlsv1`, `--no-tlsv1_1`.
- `--no-dtls` оставить: turns фактически всегда ходит по TCP.
- Volume: `/var/lib/vycord/coturn-certs:/certs:ro`.

### 2. Доставка сертификата (`deploy/coturn-cert-hook.sh`, новый)

Переиспользуем Let's Encrypt-сертификат домена `api.vycord.webvaha.ru`
(тот же хост, что в `TURN_URLS`; выпускается в `deploy.sh` через certbot).

Хук:
- копирует `fullchain.pem` и `privkey.pem` из
  `/etc/letsencrypt/live/api.vycord.webvaha.ru/` в
  `/var/lib/vycord/coturn-certs/`;
- выставляет права, при которых пользователь coturn-контейнера читает оба
  файла (точный UID образа `coturn/coturn:4.7-alpine` определить при
  реализации);
- перезапускает контейнер `vycord-coturn` (если он существует; на первом
  прогоне до `docker compose up` контейнера ещё нет — это не ошибка);
- падает с внятной ошибкой, если исходных файлов сертификата нет.

`deploy.sh`:
- устанавливает хук в `/etc/letsencrypt/renewal-hooks/deploy/` — certbot
  запускает его при каждом продлении;
- запускает хук один раз сразу после выпуска сертификата и **до**
  `docker compose up` — иначе папка сертификатов пуста и coturn не стартует.

Принятый компромисс: при продлении сертификата (~раз в 60 дней, ночью)
coturn перезапускается и активные relay-аллокации рвутся; активный звонок
у relay-клиентов падает и требует перезахода (авто-ICE-restart не
реализован — принятое ограничение).

### 3. env (`.env.prod.example`)

- В `TURN_URLS` добавить третий URL:
  `turns:api.vycord.webvaha.ru:5349?transport=tcp`
  (порядок: udp, tcp, tls; ICE пробует все параллельно).
- В комментарии о портах добавить 5349/tcp.

### 4. Скрипт проверки (`deploy/check-turn.sh`, новый)

Запускается на сервере из корня проекта после деплоя.

1. Читает `TURN_SECRET` и `TURN_URLS` из `.env.prod`; хост берёт из первого
   URL.
2. Генерирует ephemeral-креды той же схемой, что API:
   `username="<now+10min>:healthcheck"`,
   `password = base64(HMAC-SHA1(TURN_SECRET, username))` — через `openssl`.
3. Прогоняет `turnutils_uclient` через
   `docker run --rm --network host coturn/coturn:4.7-alpine` (на хост ничего
   не ставится) по трём транспортам:
   - 3478/udp (по умолчанию),
   - 3478/tcp (`-t`),
   - 5349/tls (`-S`).
   Флаг `-y` (echo через relay) — проверяется реальная аллокация и проброс
   данных, а не только открытый порт.
4. Каждая проверка печатает `OK`/`FAIL`; при любом провале — ненулевой
   exit-код и подсказка (несовпадение секрета / закрытый порт / нечитаемый
   сертификат).
5. `check-turn.sh --print` — только выводит сгенерированные креды для ручной
   вставки в Trickle ICE.

Ограничение (фиксируется в доке): скрипт работает с самого сервера, поэтому
доказывает работоспособность coturn, секрета и TLS, но не внешнюю доступность
портов — для этого ручная проверка.

### 5. Документация (раздел «TURN» в `README.md`)

- Таблица портов для фаервола: 3478/udp, 3478/tcp, 5349/tcp,
  49160–49360/udp — с готовыми командами `ufw allow`.
- Как запускать `deploy/check-turn.sh` и читать его вывод.
- Ручная проверка снаружи: страница Trickle ICE
  (webrtc.github.io/samples), вставить `turns:`-URL и креды из `--print`,
  убедиться, что появляется кандидат типа `relay`.

## Обработка ошибок

- 5349 заблокирован у клиента → ICE использует остальные кандидаты,
  деградации нет.
- Сертификаты не скопированы → coturn не стартует; `check-turn.sh` показывает
  FAIL по всем транспортам, `restart: unless-stopped` подхватывает контейнер
  после починки.
- Хук падает при продлении → certbot логирует ошибку; старый серт продолжает
  работать до истечения, есть время заметить.

## Тестирование / критерии приёмки

Нового прикладного кода нет (конфиги + bash); существующие Go-тесты
(`server/internal/usecase/turn_test.go`) не трогаем.

Приёмка на проде:
1. `deploy/check-turn.sh` — `OK` по всем трём транспортам.
2. Trickle ICE снаружи с `turns:`-URL даёт relay-кандидат.
3. Существующий звонок между двумя клиентами продолжает работать.
