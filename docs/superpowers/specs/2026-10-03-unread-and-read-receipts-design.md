# VYC-104 — Непрочитанные сообщения и статус прочтения

Дата: 2026-10-03 · Ветка: `VYC-104-show-notify-msg-any-server`

## 0. Цель и границы

Два функционала на одном механизме — **серверном курсоре прочтения**:

1. **Счётчики непрочитанных.** На иконке сервера — сумма непрочитанных по его
   каналам; в списке каналов — счётчик у каждого канала.
   ```
   Сервер 1 (10)
     - Канал 1 (3)
     - Канал 2 (7)
   ```
2. **Статус прочтения.** Под своим сообщением автор видит галочку: серую, пока
   никто не прочитал, цветную — как только прочитал хотя бы один. Автор, а
   также владелец сервера и роли с `PermAdministrator`, могут открыть список
   «Прочитали / Не прочитали».

### Решения (согласованы)

| Вопрос | Решение |
|---|---|
| Когда галочка цветная | Прочитал **≥1** участник, кроме автора |
| Кто видит список «кто прочитал» | Автор сообщения + владелец сервера + `PermAdministrator`; проверяет сервер |
| Когда сообщение прочитано | Строка сообщения видна во вьюпорте **и** окно в фокусе / вкладка видима |
| Кто в списке «Не прочитали» | Текущие участники сервера, кроме автора. Гости как читатели не учитываются |
| Гостевые сообщения | Входят в счётчик непрочитанных; галочек и списка у них нет |
| Звонковые строки (`kind = 'call'`) | Не входят в счётчик, не порождают событий, галочек нет |
| Свои сообщения | Не непрочитаны; отправка продвигает курсор автора |
| Старт после деплоя | Сид: всем курсор = `now()` — история не становится непрочитанной |
| Новый участник | Курсор по умолчанию = `server_members.joined_at` |
| Потолок счётчика | Считаем до 100, на бейдже `99+` |

### Вне рамок (YAGNI)

Mute сервера/канала; отдельная подсветка упоминаний; превью последнего
сообщения в мобильных списках (`preview` остаётся `null`); живое обновление
открытого поповера «Кто прочитал»; бейдж на иконке приложения Electron; кэш
аудитории fan-out.

### Отвергнутые подходы

- **Отметка на каждое сообщение** (`message_reads(message_id, user_id)`):
  рост «сообщения × участники», сотни вставок при прочтении пачки. Ничего не
  даёт сверх курсора, т.к. прочтение у нас «до этого места».
- **Клиентский localStorage** (нынешний `unreadStore`): не синхронизируется
  между устройствами, квитанции невозможны.

## 1. Схема БД

Миграция `029_channel_read_states` (номер сверить при мерже с ветками,
добавляющими миграции, напр. `VYC-101-audio-in-chat`).

```sql
-- +migrate Up
CREATE TABLE channel_read_states (
    user_id              UUID NOT NULL REFERENCES users(id)    ON DELETE CASCADE,
    channel_id           UUID NOT NULL REFERENCES channels(id) ON DELETE CASCADE,
    last_read_at         TIMESTAMPTZ NOT NULL,
    last_read_message_id UUID,  -- без FK: сообщение могут удалить, курсор остаётся валиден
    updated_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, channel_id)
);
CREATE INDEX idx_crs_channel ON channel_read_states (channel_id, last_read_at);
CREATE INDEX IF NOT EXISTS idx_messages_channel_created ON messages (channel_id, created_at);

-- Сид: всё существующее считается прочитанным.
INSERT INTO channel_read_states (user_id, channel_id, last_read_at)
SELECT sm.user_id, c.id, now()
FROM server_members sm JOIN channels c ON c.server_id = sm.server_id
ON CONFLICT DO NOTHING;

-- +migrate Down
DROP INDEX IF EXISTS idx_messages_channel_created;
DROP TABLE IF EXISTS channel_read_states;
```

### Семантика курсора

- **Эффективный курсор** пользователя U в канале C: строка
  `channel_read_states`, а при её отсутствии — `(server_members.joined_at, NULL)`.
  Новый канал и новый участник работают без явной вставки.
- **Порядок сообщений** — лексикографическая пара `(created_at, id)`.
  Сообщение M прочитано пользователем U ⇔ `(M.created_at, M.id) ≤ курсор U`.
  Для курсора с `last_read_message_id = NULL` сравнение только по времени
  (`M.created_at ≤ last_read_at`).
- **Только вперёд:** upsert меняет строку, лишь если новая пара строго больше
  текущей. Повторные и запоздавшие запросы безопасны.

### Непрочитанные для пользователя `$me` в канале C

```
kind = 'user'
AND user_id IS DISTINCT FROM $me          -- гостевые (user_id NULL) считаются
AND (created_at, id) > эффективный курсор
LIMIT 100                                  -- во вложенном запросе на канал
```

Один запрос возвращает счётчики по всем каналам всех серверов пользователя.

## 2. HTTP API

Все маршруты под `authMid.RequireAuth`; доступ к каналу — существующая проверка
членства / `PermViewChannels`.

| Метод | Путь | Ответ / поведение |
|---|---|---|
| `GET` | `/api/v1/unread` | `[{server_id, channel_id, count, last_read_at, last_read_message_id}]` по всем каналам всех моих серверов |
| `PUT` | `/api/v1/channels/{channel_id}/read` | Тело `{message_id}`. Сервер берёт `created_at` сообщения сам; сообщение должно принадлежать каналу (иначе 404/400). Upsert только вперёд. Ответ `{count, last_read_at, last_read_message_id}` — `count` = непрочитанные после итогового курсора |
| `GET` | `/api/v1/channels/{channel_id}/read-receipts` | `{others_max_read_at, others_max_read_message_id}` — максимальный **явный** курсор (строка `channel_read_states`) среди участников сервера, кроме меня. Кто именно — не раскрывается |
| `GET` | `/api/v1/channels/{channel_id}/readers/{message_id}` | `{read: [user], unread: [user]}` — текущие участники сервера без автора; «прочитал» = явный курсор дошёл до сообщения. **403**, если вызывающий не автор, не владелец и без `PermAdministrator`; **403** для гостевого и звонкового сообщения |

`user` — та же публичная форма пользователя, что в списке участников
(`id, username, avatar_url`).

Курсор автора продвигается на созданное сообщение синхронно в хендлере сразу
после создания (нотификатор `ChannelActivityNotifier.Created`, он же шлёт
`channel_activity`) — без изменения сигнатуры `NewMessageUseCase`.

Маршрут читателей — `/readers/{message_id}`, а не `/messages/{message_id}/readers`:
второй шаблон конфликтует в `net/http` ServeMux с существующим
`/messages/around/{message_id}` (паника при регистрации).

Квитанции и список читателей учитывают только явные курсоры, без фолбэка на
`joined_at`: иначе участник, вступивший после сообщения, «прочитал» бы его.
Счётчики непрочитанного фолбэк используют.

Время создания сообщения (участником и гостем) усекается до микросекунд —
точности Postgres, — чтобы время в ответе/WS совпадало с временем в БД.

### Раскладка кода (существующие слои)

- `internal/domain/readstate.go` — типы, интерфейс репозитория, ошибки.
- `internal/usecase/readstate.go` — правило «только вперёд», проверка
  принадлежности сообщения каналу, права на `readers`, подсчёт.
- `internal/repository/postgres/readstate.go` — SQL.
- `internal/delivery/http/handler/readstate.go` — хендлеры; маршруты в
  `cmd/api/main.go` рядом с маршрутами сообщений.

## 3. WS-события

Существующие `chat_message` / `message_update` / `message_delete` остаются
`SendToChannel`. Новые события лёгкие, без текста сообщения.

### `channel_activity` → все онлайн-участники сервера

```json
{ "type": "channel_activity",
  "payload": { "op": "create", "server_id": "…", "channel_id": "…",
               "message_id": "…", "created_at": "…", "author_user_id": "…|null" } }
```

- `op: "create"` — при создании сообщения участником (`handler/message.go`) и
  гостем (`handler/guest.go`); `op: "delete"` — при удалении.
- Звонковые строки событие не порождают.
- Аудитория — тот же путь, что `h.broadcast(serverID, …)` в
  `handler/server.go` (участники сервера → `hub.SendToUsers`). Резолв
  аудитории выносится в общий хелпер, используемый обоими хендлерами.

### `channel_read` → открывшие канал (`SendToChannel`), кроме читателя

```json
{ "type": "channel_read",
  "payload": { "channel_id": "…", "read_at": "…", "message_id": "…" } }
```

Шлётся после `PUT /read`, только если курсор сдвинулся. Id читателя в событии
нет.

### Синхронизация

- После каждого (ре)коннекта WS клиент делает полный `GET /unread`: дельты
  могут разъехаться (пропуск события, гонка с удалением), курсоры — серверные.
- Хаб держит одну сессию на `user_id`, поэтому отдельного кросс-девайс события
  нет: другое устройство получит счётчики при переподключении.
- `server_delete` / `channel_delete` / выход из сервера: клиент выбрасывает
  счётчики; строки курсоров удаляет `ON DELETE CASCADE`.

## 4. Клиент

### `stores/unreadStore.ts` — переписывается на серверный курсор

```ts
channels:   Record<channelId, { serverId, count, lastReadAt, lastReadMessageId }>
othersRead: Record<channelId, { at, messageId }>
hydrate()                 // GET /unread — при логине и каждом (ре)коннекте WS
applyActivity(ev)         // channel_activity
applyChannelRead(ev)      // channel_read: othersRead = max(текущее, событие)
markRead(channelId, msg)  // оптимистично двигает курсор; PUT /read с дебаунсом ~1 с;
                          // count берётся из ответа сервера
selectServerUnread(id)    // сумма count по каналам сервера
```

`applyActivity`:
- `create`: `+1`, если автор не я и `(created_at, id)` > моего курсора. Если
  канал открыт, окно в фокусе и сообщение видно — трекер прочтения сам
  продвинет курсор (ответ `PUT` выровняет счётчик).
- `delete`: `−1` при тех же условиях, не ниже нуля.

Старый ключ `vycord.lastRead` один раз удаляется из localStorage.
`firstUnreadId` и разделитель «новые сообщения» в `ChatArea` сохраняются,
источник курсора — стор.

Подписки на `channel_activity` / `channel_read` — в `pages/app/useAppController.ts`
рядом с существующими.

### `useReadTracker(channelId, containerRef)` — детект прочтения

- Заменяет нынешний `IntersectionObserver` на нижнем маячке в `ChatArea`.
- `IntersectionObserver` на строках сообщений (`data-message-id`): строка
  «видна», когда её нижний край во вьюпорте.
- Прочитанным считается только при `document.hasFocus()` и
  `document.visibilityState === 'visible'`. Без фокуса видимые строки копятся
  как кандидаты; на `focus` / `visibilitychange` фиксируются те, что всё ещё
  видны.
- Курсор = самое позднее зафиксированное сообщение; только вперёд.
- Пропускаются: `kind: 'call'`, сообщения с `deliveryState`, сообщения не
  этого канала (защита от гонки при переключении — см. комментарий в нынешнем
  `ChatArea`).
- Используется в `ChatArea` и в мобильном `ChatScreen`.

### Бейджи

- `ServerList` — бейдж суммы непрочитанных на иконке сервера, `99+`.
- `ChannelSidebar` — пилюля со счётчиком справа от имени, имя жирное при
  `count > 0`.
- Мобильная версия: меняются только тела `useChannelActivity` /
  `useServerActivity` в `mobile/activity.ts` — возвращают `unreadCount` из
  стора (`hasUnread = count > 0`, `preview: null`, `timestamp: null`).
  `ActivityMeta` рендерит уже готовый бейдж.
- Стили — токены и правила `client/docs` (дизайн-система), без новых цветов.

### Галочки

- Только на своих сообщениях `kind: 'user'` без `deliveryState`.
- Серая ✓ — пока `(created_at, id) > othersRead[channel]`; цветная (акцентный
  токен) — иначе.
- `othersRead` грузится `GET /read-receipts` при входе в канал, дальше —
  событиями `channel_read`.

### «Кто прочитал»

- Десктоп — компактная модалка (`.modal-overlay` + `useModalFocus`), мобильный —
  `BottomSheet`; содержимое общее.
- Открытие: клик по галочке (автор); кнопка «Кто прочитал» в hover-панели
  сообщения (контекстного меню у сообщений нет) — для автора, владельца и
  `PermAdministrator` (админ — и на чужих сообщениях). Для гостевых и
  звонковых сообщений кнопки нет.
- Содержимое: «Прочитали (N)» и «Не прочитали (M)» — аватар + имя. Загрузка
  `GET …/readers` при открытии; состояния загрузки и ошибки. 403 → пункт
  скрыт/поповер закрывается с ошибкой.
- Мобильная версия: долгий тап по сообщению → «Кто прочитал» → нижняя шторка
  с тем же списком.

### i18n

Все новые строки — в `i18n/locales/ru.ts` и `en.ts`.

## 5. Тестирование

### Сервер

- **Usecase (моки)**: курсор только вперёд; сообщение из чужого канала
  отвергается; `readers` — 403 для не-автора без прав, 403 для гостевого и
  звонкового; автор продвигает курсор при отправке.
- **Репозиторий (реальная Postgres)**: подсчёт — исключение звонков и своих,
  учёт гостевых, потолок 100, фолбэк на `joined_at`, совпадающий `created_at`
  (порядок по `id`); `readers` — разбиение участников; `others_max`;
  миграция up/down и сид.
- **Хендлеры**: `channel_activity` create/delete (включая гостевой путь)
  уходит участникам сервера; `channel_read` — только при сдвиге курсора.
- Гейты `make test vet lint build`; базовую линию для Go замерить на ветке до
  изменений.

### Клиент

- **Стор**: `hydrate`, `applyActivity` (±1, своё сообщение, не ниже нуля),
  `applyChannelRead` (только max), `selectServerUnread`, `99+`, удаление
  старого ключа localStorage; существующие тесты `firstUnreadId` сохраняются.
- **`useReadTracker`** (мок `IntersectionObserver` и фокуса): без фокуса курсор
  не двигается, на `focus` фиксируется; только вперёд; пропуск звонков и
  pending; дебаунс `PUT`.
- **Компоненты**: цвет галочки по `othersRead`; поповер — секции, загрузка,
  403.
- **Визуальная проверка** CDP-харнессом (`client/tools/verify`, правила
  `client/docs/verification.md`): бейджи сервера и канала, галочки, поповер,
  мобильные экраны.
- Гейты `tsc`, `stylelint`, `check:i18n`, `npm test` (ровно 3 известных падения
  в `api.network-retry.test.ts`).
- **Ручной e2e, два аккаунта**: А пишет → у Б растут счётчики сервера и канала;
  Б открывает канал при свёрнутом окне → галочка у А серая; Б фокусирует окно →
  галочка цветная, счётчики у Б обнуляются; А открывает «Кто прочитал»;
  реконнект Б → счётчики сходятся с сервером.

## 6. Порядок реализации

1. Миграция, домен, репозиторий, usecase + тесты.
2. HTTP-эндпоинты; продвижение курсора автора в `CreateMessage`.
3. WS-события `channel_activity` / `channel_read`, включая гостевой путь.
4. Клиент: стор и API-слой, гидратация, подписки WS.
5. `useReadTracker` вместо текущего наблюдателя в `ChatArea` (+ мобильный чат).
6. Бейджи: `ServerList`, `ChannelSidebar`, мобильные хуки `activity.ts`.
7. Галочки и поповер «Кто прочитал» (десктоп + мобильная шторка).
8. i18n, визуальная проверка, ручной e2e.

После шага 6 функционал 1 (счётчики) работоспособен целиком — точка, где ветку
можно разрезать, если понадобится выкатка частями.
