# Аватар пользователя с загрузкой и кропом

**Задача:** дать пользователю возможность загрузить и обновить свой аватар (PNG/JPG/JPEG, ≤2 МБ) с кропом области фото перед сохранением. Для этого выделяется отдельный раздел «Профиль» в настройках пользователя — задел на будущие персональные настройки/данные.

**Дата:** 2026-07-21
**Ветка:** `VYC-42` (текущая)

## Проблема

В БД и доменной модели (`domain.User.AvatarURL`, `users.avatar_url`) поле аватара уже существует, но нигде не используется — во всех местах интерфейса (сайдбар, список участников, чат, голосовые каналы) вместо аватара везде рендерится цветной кружок с первой буквой username. Механизма загрузки файлов в проекте нет вообще: ни S3, ни локального хранилища, ни соответствующих эндпоинтов. Настройки пользователя (`Settings.tsx`) — единственное модальное окно с секциями Audio/Video/Appearance в общем скролле, без раздела профиля.

## Решение

### 1. UX и структура клиента

**Settings → табы в духе Discord.** `Settings.tsx` перестраивается: слева вертикальный список вкладок, справа — контент выбранной. Существующие секции выносятся как есть в отдельные компоненты без изменения логики:

- `client/src/components/settings/ProfileSettings.tsx` — **новая**, первая вкладка
- `client/src/components/settings/AudioSettings.tsx` — текущее содержимое секции Audio
- `client/src/components/settings/VideoSettings.tsx` — текущее содержимое секции Video
- `client/src/components/settings/AppearanceSettings.tsx` — текущее содержимое секции Appearance

`Settings.tsx` становится тонкой оболочкой: модалка + список вкладок + рендер выбранной.

**Вкладка «Профиль» (`ProfileSettings.tsx`):**
- крупный круглый аватар (текущее фото или инициалы) сверху;
- кнопка «Изменить аватар» → скрытый `<input type="file" accept="image/png,image/jpeg">`;
- сразу после выбора файла — клиентская проверка формата и размера (см. «Валидация» ниже); при ошибке — инлайн-сообщение, кроппер не открывается;
- при успешной проверке — открывается `AvatarCropModal`;
- кнопка «Удалить аватар» (видна, только если аватар установлен) — вызывает `DELETE`, возвращает дефолтные инициалы;
- ниже — блок username/email в режиме read-only (задел под будущие поля профиля, которые сюда же добавятся отдельными задачами).

**Кроп-модалка `client/src/components/AvatarCropModal.tsx`** (+ `.css`), свой canvas-компонент без внешних зависимостей:

```tsx
interface AvatarCropModalProps {
  file: File;
  onCancel: () => void;
  onSave: (blob: Blob) => void; // уже обрезанное, финальное изображение
}
```

- фото рисуется на `<canvas>`, поверх — круглая маска (затемнение вне круга);
- перетаскивание (`mousedown`/`mousemove`/`touchmove`) панорамирует изображение внутри рамки;
- зум — `<input type="range">` плюс прокрутка колёсиком мыши по канвасу;
- ограничение пана/зума: изображение не может отодвинуться так, чтобы в круге появилась пустая область (масштаб не может быть меньше того, что покрывает круг целиком);
- кнопки «Сохранить» / «Отмена»;
- «Сохранить» рендерит финальный кроп на отдельном офскрин-канвасе 512×512 и экспортирует через `canvas.toBlob('image/jpeg', 0.92)` — экспорт всегда в JPEG независимо от формата исходника, это упрощает и клиентскую, и серверную обработку.

**Общий компонент `client/src/components/Avatar.tsx`:**

```tsx
interface AvatarProps {
  url?: string;
  username: string;
  size?: 'sm' | 'md' | 'lg';
  online?: boolean; // сохраняет текущий индикатор онлайн-статуса, где он есть
}
```

Рендерит `<img>`, если `url` задан (с `onError`, откатывающим на инициалы при неудачной загрузке картинки), иначе — существующий кружок с первой буквой username и тем же набором CSS-классов/модификаторов, что и сейчас. Заменяет собой ручные `<div className="user-avatar ...">{initial}</div>` в:
- `ChannelSidebar.tsx` (user-panel, voice-participant-avatar);
- `UserList.tsx` (список участников);
- `ChatArea.tsx` (аватар автора сообщения).

### 2. Backend: хранение файлов и API

**Хранилище** — пакет `server/pkg/filestorage`:

```go
type Storage interface {
    Save(ctx context.Context, key string, r io.Reader, contentType string) (url string, err error)
    Delete(ctx context.Context, key string) error
}
```

Реализация `local.go` пишет файлы в директорию `UPLOAD_DIR` (новая переменная окружения, дефолт `./uploads`), URL вида `/uploads/avatars/{userID}/{random-hex}.jpg`. Случайный суффикс в ключе означает, что при каждой смене аватара получается новый URL — браузерное кэширование по URL не мешает увидеть новую картинку, инвалидировать ничего не нужно. Интерфейс закладывает возможность добавить S3-реализацию в будущем (см. борду) без изменений в хендлерах.

**Раздача файлов:** в `cmd/api/main.go` — `router.Handle("GET /uploads/", http.StripPrefix("/uploads/", http.FileServer(http.Dir(uploadDir))))`. Nginx-конфиги менять не нужно: текущий `location /` в `api.vycord.webvaha.ru.conf` уже проксирует всё, кроме `/ws` и `/sfu/ws`, на API.

**Эндпоинты** в существующем `UserHandler` (`server/internal/delivery/http/handler/user.go`), под `authMid.RequireAuth`:

- `POST /api/v1/users/me/avatar` — `multipart/form-data`, поле `avatar`. Обработка по шагам:
  1. `http.MaxBytesReader(w, r.Body, maxAvatarSize)` — жёсткий лимит на тело запроса (2 МБ + небольшой запас на multipart-обвязку);
  2. чтение файла из multipart;
  3. определение реального типа через `http.DetectContentType` по первым байтам (Content-Type от клиента не доверенный) — допускаются только `image/png` и `image/jpeg`;
  4. `image.DecodeConfig` — файл должен декодироваться как валидное изображение; дополнительно проверяются разумные границы разрешения (не меньше 32×32, не больше 4096×4096) — защита от файлов с маленьким весом, но экстремальным разрешением;
  5. сохранение через `filestorage.Storage.Save` с ключом `avatars/{userID}/{random}.jpg`;
  6. обновление `avatar_url` в БД через существующий `userRepo.Update(id, map[string]interface{}{"avatar_url": newURL})`;
  7. если у пользователя был предыдущий файл — удаление его через `Storage.Delete` (после успешного обновления БД);
  8. бродкаст `user_updated` всем подключённым клиентам через hub;
  9. ответ — обновлённый `domain.User` (как в остальных хендлерах, с очищенным паролем).
- `DELETE /api/v1/users/me/avatar` — очищает `avatar_url` (`nil`), удаляет файл, бродкастит `user_updated` с `avatar_url: null`, отвечает обновлённым `User`.

Порядок «сначала файл на диск, потом запись в БД» намеренный: если БД-апдейт упадёт после успешной записи файла, останется один orphan-файл (не критично, чистится вручную/будущей джобой) — это проще и безопаснее, чем распределённая транзакция или откат файла при ошибке БД.

**Hub:** новый метод `BroadcastUserUpdate(userID uuid.UUID, avatarURL *string)` в `server/internal/delivery/ws/hub.go`, по образцу существующего `BroadcastVoiceParticipants` — шлёт всем клиентам `{type: "user_updated", payload: {id, avatar_url}}` через `h.BroadcastMessage`.

### 3. Клиент: загрузка и live-обновление

**`client/src/services/api.ts`** — новые методы:
- `uploadAvatar(blob: Blob): Promise<User>` — `POST /users/me/avatar`, `FormData` с полем `avatar`;
- `removeAvatar(): Promise<User>` — `DELETE /users/me/avatar`.

**`authStore.ts`** — новый экшен `updateUser(patch: Partial<User>)`, мёржит патч в `user` и синхронизирует `localStorage` (аналогично существующему `login`). `ProfileSettings` вызывает его сразу после успешного ответа `uploadAvatar`/`removeAvatar`, чтобы у себя самого аватар обновился без ожидания WS round-trip.

**`AppPage.tsx`** — по аналогии с уже существующими глобальными подписками (`voice_state`, `voice_participants`) добавляется:
```ts
wsService.on('user_updated', (payload) => {
  const { id, avatar_url } = payload as { id: string; avatar_url: string | null };
  if (id === authStore.getState().user?.id) {
    authStore.getState().updateUser({ avatar_url: avatar_url ?? undefined });
  }
  serverStore.getState().patchMemberAvatar(id, avatar_url);
});
```

**`serverStore.ts`** — новый экшен `patchMemberAvatar(userId: string, avatarUrl: string | null)`, точечно обновляет `avatar_url` нужного элемента в `members` (используется `ChatArea` для аватаров других авторов сообщений).

**`UserList.tsx`** — добавляется `wsService.on('user_updated', loadOnlineUsers)` в общий список триггеров рефетча (`user_joined`/`user_left`/`online_users`), по уже принятому в компоненте паттерну.

## Валидация и обработка ошибок

**Клиент (быстрая обратная связь до открытия кроппера):**
- MIME/расширение не из `{image/png, image/jpeg}` → «Неподдерживаемый формат. Разрешены PNG, JPG, JPEG»;
- размер файла > 2 МБ → «Файл слишком большой. Максимум 2 МБ».

**Сервер (источник истины, клиенту не доверяем):**
- тело запроса превышает лимит → `413`;
- `http.DetectContentType` вне `{image/png, image/jpeg}` → `400 unsupported format`;
- `image.DecodeConfig` не смог разобрать файл → `400 invalid image`;
- разрешение вне границ 32×32..4096×4096 → `400 invalid image dimensions`;
- ошибка записи на диск → `500`, без изменения `avatar_url` в БД.

**Клиент при ошибке загрузки:** сообщение об ошибке остаётся внутри открытой кроп-модалки (текст ошибки зависит от кода: 413 → «файл слишком большой», прочее → «не удалось загрузить, попробуйте ещё раз»), модалка не закрывается, доступна повторная попытка «Сохранить» без повторного выбора файла и повторного кропа.

## Тестирование

**Backend (Go, по образцу `server/internal/delivery/http/handler/user_test.go`):**
- хендлер: успешная загрузка (200, `avatar_url` обновился, старый файл удалён), превышение размера (413), неверный MIME/расширение (400), битый файл под видом изображения (400), экстремальное разрешение (400);
- `DELETE`: `avatar_url` очищается, файл удаляется, повторный `DELETE` без аватара не падает;
- `filestorage.Local`: `Save`/`Delete` на временной директории (happy path + удаление несуществующего ключа).

**Frontend:** отдельного тест-фреймворка для юнит/компонентных тестов в клиенте нет (есть только Playwright e2e для звонков) — автотесты на кроппер и `ProfileSettings` не заводятся, вместо этого ручной QA в браузере перед сдачей:
- happy path: выбор файла → кроп → сохранение → аватар виден у себя во всех местах интерфейса;
- отклонение файла неверного формата и файла > 2 МБ с понятной ошибкой;
- отмена кропа не отправляет запрос и не меняет аватар;
- удаление аватара возвращает инициалы;
- два открытых клиента (вкладки/браузера) — у второго аватар первого обновляется вживую после сохранения, без релоада;
- поведение кроппера (пан/зум/границы) на разных пропорциях исходного фото (широкое, узкое, маленькое < 512px);
- повторная попытка после сетевой ошибки не требует заново выбирать файл.

## Деплой

`UPLOAD_DIR` должен указывать на персистентный том, переживающий передеплой API (не на путь внутри артефакта сборки/контейнера, если такой появится). В рамках этой задачи сам деплой-пайплайн не меняется — только добавляется требование к окружению, фиксируется как заметка для следующего шага настройки прода.

## Вне скоупа

- Остальные поля профиля (био, смена username/email, соцсети) — вкладка «Профиль» закладывает место под них, но в этой задаче реализуется только аватар.
- S3/облачное хранилище — интерфейс `filestorage.Storage` это допускает, но реализация остаётся локальной; отдельная задача на борде.
- Ресайз/рекомпрессия на сервере сверх валидации — клиент уже отдаёт нормализованный кроп 512×512 JPEG, сервер не переобрабатывает изображение, только проверяет.
- Множественные размеры аватара (thumbnail/full) — везде используется один и тот же файл 512×512.
- Модерация/проверка содержимого загружаемых изображений — не требуется для этой задачи.
