# VYC-25: JWT-аутентификация на SFU signaling (`/ws`)

**Дата:** 2026-07-08
**Статус:** утверждено

## Проблема

SFU принимает WebSocket-подключения на `/ws` без какой-либо аутентификации:
`user_id` и `room_id` берутся из query-параметров как есть
(`server/internal/sfu/transport/signaling/handler.go`). Любой, кто знает
`room_id`, может подключиться к чужой комнате под произвольным `user_id`.

## Объём

- **Входит:** аутентификация подключения к SFU по JWT; идентичность
  пользователя — только из claims токена.
- **Не входит:** проверка членства в сервере/канале (отдельная задача на
  борде), ревокация токенов / refresh tokens (отдельная задача),
  ограничение `CheckOrigin` (отдельная задача).

## Решения

| Вопрос | Решение |
| --- | --- |
| Объём | Только аутентификация, без проверки членства |
| Транспорт токена | Query-параметр `?token=` — тот же паттерн, что у чатового WS API (`/ws?token=`) |
| Валидация на SFU | Stateless: SFU сам проверяет подпись HMAC и `exp` общим `JWT_SECRET`, без БД и сетевых вызовов |

Отклонённые альтернативы: introspection через API (связность и латентность на
каждое подключение), короткоживущий room-токен от API (правильный задел под
членство, но шире объёма VYC-25).

## Дизайн

### 1. Общий пакет валидации — `server/pkg/authtoken`

Функция `ValidateToken(secret, tokenString string) (uuid.UUID, error)`:

- парсит JWT, допускает только метод подписи HMAC (защита от `alg=none`
  и подмены алгоритма);
- проверяет валидность (включая `exp`);
- достаёт и парсит `user_id` из claims, возвращает `uuid.UUID`.

Это извлечение существующей логики из `usecase/auth.go` (`ValidateToken`).
Auth-usecase рефакторится на использование пакета: парсинг через
`pkg/authtoken`, затем свой поход в `userRepo`. Одна реализация парсинга
вместо двух расходящихся копий.

### 2. SFU

- `cmd/sfu/main.go`: читает `JWT_SECRET` из env; если пуст — завершение с
  ошибкой (fail-fast, как в config API). Секрет передаётся в
  `signaling.NewHandler`.
- `signaling/handler.go` (`ServeHTTP`), до upgrade:
  - из query берутся `token` и `room_id`;
  - нет токена → `401 Unauthorized`; нет `room_id` → `400 Bad Request`;
  - невалидный/истёкший токен → `401 Unauthorized`, warn в лог без
    содержимого токена;
  - `user_id` берётся из claims; query-параметр `user_id` удаляется
    полностью.
- Неиспользуемое поле `UserID` в `JoinPayload` (`protocol.go`) удаляется —
  не оставляем второй недоверенный источник идентичности.
- Деплой не меняется: SFU-контейнер уже получает `.env.prod` целиком через
  `env_file` (docker-compose.prod.yml), `JWT_SECRET` ему доступен.

### 3. Клиент

- `client/src/services/groupCall.ts`: URL подключения меняется на
  `${SFU_URL}/ws?room_id=${roomId}&token=${token}`; токен читается из
  localStorage (`vycord_token`) так же, как в `websocket.ts`.
- VYC-24 reconnect: токен перечитывается на каждой попытке rejoin, а не
  замораживается в момент первого join.

### 4. Ошибки и граничные случаи

- Отказ происходит до WebSocket-upgrade — соединение не устанавливается.
- Истечение токена посреди звонка не рвёт активную сессию: проверка только
  на подключении. Провал reconnect по истёкшему токену ведёт себя как
  текущий чатовый WS — пользователь перелогинивается.
- Токен в URL может попадать в access-логи nginx — осознанный компромисс,
  идентичный уже существующему паттерну чатового WS.

### 5. Тесты

- Unit `pkg/authtoken`: валидный токен; истёкший; чужая подпись; `alg=none`;
  отсутствующий или невалидный `user_id` в claims.
- Хендлер SFU через `httptest`: без токена → 401; мусорный токен → 401;
  валидный токен → успешный upgrade и join.
- E2E `client/e2e` ходят на реальный SFU — обновить подключение, чтобы
  передавался валидный токен (как именно они сейчас подключаются —
  выяснить на этапе плана).
