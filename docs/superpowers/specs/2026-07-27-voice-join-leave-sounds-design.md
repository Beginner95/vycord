# VYC-49 — Звуковые уведомления о входе и выходе участников звонка

**Дата:** 2026-07-27
**Ветка:** `VYC-49-song-in-enter-user`
**Область:** только групповой звонок (`services/audio.ts`, `services/groupCall.ts`, `components/GroupCallUI.tsx`, `components/settings/AudioSettings.tsx`). Звонок 1-на-1 (`call.ts` / `CallUI`) не затрагивается — там всего два участника и уже есть свои сигналы (`playCallAccepted` / `playCallEnded` / `playBusy`). Серверная часть не меняется.

## Цель

Во время группового звонка участники должны на слух понимать, что кто-то вошёл в звонок или вышел из него, не глядя в интерфейс. Два разных сигнала: восходящий на вход, зеркальный нисходящий на выход.

## Ключевое решение (семантика)

`GroupCallCallbacks.onPeerJoined` сейчас вызывается из **двух** разных мест `groupCall.ts` и означает две разные вещи:

1. из снапшота `joined.existing_peers` — «этот участник УЖЕ был в комнате, когда я вошёл». Срабатывает при своём входе **и на каждой успешной попытке авто-реконнекта** (`reconnect()` → `connect()` → та же ветка `'joined'`, при этом `onReconnecting` предварительно чистит список участников в UI);
2. из живого события `participant_joined` — «участник вошёл только что, я это вижу в реальном времени».

Звук должен играть **только во втором случае**. Поэтому колбэк получает явный параметр источника:

```ts
onPeerJoined: (userId: string, source: 'snapshot' | 'live') => void;
```

Сервис уже знает, из какой ветки пришло событие, — знание не выводится по таймингам, а передаётся. Отвергнутые альтернативы:

- **временное окно глушения в UI** (игнорировать входы N мс после старта join/reconnect) — хрупко в обе стороны: реальный вход внутри окна проглатывается, поздно пришедший снапшот озвучивается;
- **диффинг множества «известных пиров» в UI** — требует сигнала «снапшот закончился», которого в протоколе сигналинга нет.

`onPeerLeft` менять не нужно: `participant_left` приходит только по живому WS. Во время реконнекта WS закрыт, а те, кто ушёл за время простоя, просто отсутствуют в снапшоте — ложных «выходов» не бывает по конструкции.

## Архитектура

```
groupCall.ts
  'joined'.existing_peers ──→ onPeerJoined(uid, 'snapshot') ──→ (звука нет)
  'participant_joined'    ──→ onPeerJoined(uid, 'live')     ──→ audioService.playUserJoined()
  'participant_left'      ──→ onPeerLeft(uid)               ──→ audioService.playUserLeft()

GroupCallUI.tsx
  handleJoinGroupCall  (свой вход, тот же предикат, что у voice_joined) ──→ playUserJoined()
  handleLeaveGroupCall (свой выход по кнопке)                           ──→ playUserLeft()
```

## Компоненты

### 1. `client/src/services/audio.ts` — два новых сигнала

Пара тонов на осцилляторе `triangle` — тембр отличается от `sine`, которым играют сообщения и сигналы P2P-звонка:

- `playUserJoined()` — восходящая: E5 659.25 Гц (80 мс) → A5 880 Гц (160 мс)
- `playUserLeft()` — зеркальная нисходящая: A5 880 Гц (80 мс) → E5 659.25 Гц (200 мс)

Громкость `settings.volume * 0.25` — тише сигнала сообщений, потому что звучит поверх живого разговора.

Приватный `playTone` получает необязательный шестой параметр `type: OscillatorType = 'sine'`; существующие вызовы не меняются.

**Антидребезг.** Приватное поле `lastVoiceSoundAt: { joined: number; left: number }` (значения `performance.now()`). Повторный сигнал того же типа в пределах **250 мс** подавляется (не откладывается в очередь, а отбрасывается). Это даёт корректное поведение при пачке одновременных событий — двое вошли в одну секунду, звучит один сигнал — и служит вторым эшелоном обороны против снапшот-шторма, если логика источника когда-нибудь регрессирует.

**Настройка.** Новое поле `voiceSound: boolean` в интерфейсе `AudioSettings` и в `DEFAULT_SETTINGS` со значением `true`; персистится в тот же ключ `vycord_audio_settings` (существующий `{ ...DEFAULT_SETTINGS, ...JSON.parse(stored) }` в конструкторе корректно подставит дефолт пользователям со старым сохранённым объектом). Оба новых метода начинаются с `if (!this.settings.voiceSound) return;`.

Тип `NotificationType` расширяется значениями `'user_joined' | 'user_left'` для консистентности (тип экспортируется, но нигде не используется как дискриминатор — расширение чисто описательное).

### 2. `client/src/services/groupCall.ts` — источник события

- В `GroupCallCallbacks` сигнатура `onPeerJoined` получает второй параметр `source: 'snapshot' | 'live'`.
- В ветке `'joined'` (перебор `existing_peers`) передаётся `'snapshot'`.
- В `handleMessage`, `case 'participant_joined'`, передаётся `'live'`.

Других потребителей колбэка в коде нет — `GroupCallUI` единственный, кто вызывает `groupCallService.init`. E2E-страницы (`client/e2e/*.html`) — обычный JS без проверки типов, дополнительный аргумент для них безвреден.

### 3. `client/src/components/GroupCallUI.tsx` — четыре точки вызова

| Событие | Место | Действие |
|---|---|---|
| Чужой вход | `onPeerJoined` | `playUserJoined()` **только при `source === 'live'`** |
| Чужой выход | `onPeerLeft` | `playUserLeft()` |
| Свой вход | `handleJoinGroupCall`, внутри существующего `if (!alreadyInThisRoom && groupCallService.currentRoomIdState === roomId)` | `playUserJoined()` |
| Свой выход | `handleLeaveGroupCall`, в ветке `if (channelId)` | `playUserLeft()` |

Свой вход вешается ровно на тот предикат, который уже используется для отправки `voice_joined`: он отсекает и повторный клик по активному голосовому каналу, и узкое окно посреди реконнекта, когда `inCall` кратковременно `false`, а `currentRoomId` ещё указывает на переподключаемую комнату.

Свой выход озвучивается **только** в `handleLeaveGroupCall` (пользователь нажал кнопку выхода). В `onCallEnded` и `onError` звука нет намеренно: обрыв связи, `session_replaced` и исчерпанный лимит попыток реконнекта — это не «участник покинул звонок», а сбой соединения, и требование «не воспроизводить при изменении состояния соединения» относится в первую очередь к ним.

AudioContext на всех четырёх путях уже разблокирован: любой из них наступает после клика пользователя (вход в канал), а `getAudioContext()` дополнительно вызывает `resume()` для suspended-контекста.

### 4. `client/src/components/settings/AudioSettings.tsx` — тумблер

- Локальный `useState` `voiceSound`, инициализация из `audioService.getSettings()` в существующем `useEffect`.
- Новая строка настройки «Voice Join/Leave Sounds» с описанием «Play a sound when someone joins or leaves a voice call» и чекбоксом в том же стиле, что у Message/Call Sounds; `onChange` → `audioService.updateSettings({ voiceSound: ... })`.
- В блок «Test Sounds» добавляются две кнопки превью: `playUserJoined()` и `playUserLeft()`.

## Проверка

Юнит-раннера на клиенте нет (в `package.json` только `test:e2e` → `client/e2e/run.sh`: сборка реального Go SFU, vite dev server, headless Chrome, каждый сценарий печатает одну строку `E2E_RESULT {json}`). Поэтому проверка двухуровневая.

### E2E-сценарий `client/e2e/join-leave-events.html`

Регистрируется в `run.sh` строкой `run_scenario "join-leave-events" "http://localhost:$VITE_PORT/e2e/join-leave-events.html"` по образцу существующих сценариев.

Страница не проверяет звук как звук (это несущественная часть) — она проверяет ровно то, где есть риск: **семантику `source`** на реальном пути сигналинга.

Каркас берётся из `no-camera-screenshare.html`: фейки `getUserMedia`/`enumerateDevices` ставятся до импорта сервиса, JWT подписывается через WebCrypto секретом `e2e-test-secret` и кладётся в `localStorage`. Класс `GroupCallService` не экспортируется — три независимых участника получаются тем же приёмом, что и в существующей странице: модуль импортируется трижды с разными query-строками (`import('/src/services/groupCall.ts?inst=a')`, `?inst=b`, `?inst=c`), каждый импорт даёт Vite-модуль со своим синглтоном. Каждому передаётся свой набор колбэков, записывающий последовательность событий `(userId, source)`.

Утверждения:

1. A входит в пустую комнату → у A ноль событий `onPeerJoined`.
2. B входит → у A ровно одно событие с `source === 'live'` (userId = B); у B ровно одно событие с `source === 'snapshot'` (userId = A) и ни одного `'live'`.
3. C входит → у A и у B по одному новому `'live'` (userId = C); у C два `'snapshot'` и ноль `'live'`.
4. C уходит (`leaveGroupCall`) → у A и B по одному `onPeerLeft` с userId = C.
5. У A принудительно закрывается WS — имитация обрыва сети: приватные поля TS в рантайме обычные, поэтому странице достаточно `a.ws.close()`, что уводит сервис в `reconnect('ws_closed')` (первая попытка через 500 мс). После успешного авто-реконнекта A получает только события с `source === 'snapshot'` и **ни одного** `'live'`. Это главный регрессионный барьер фичи.

`pass: true` только если выполнены все пять пунктов.

### Ручной чек-лист (два-три реальных клиента)

- вход участника слышен остальным, выход слышен остальным, сигналы различимы на слух;
- свой вход и свой выход слышны самому пользователю;
- несколько последовательных входов/выходов озвучиваются корректно, без наложения каши;
- тумблер «Voice Join/Leave Sounds» выключает только эти звуки, рингтон и звук сообщений продолжают работать; состояние сохраняется после перезапуска приложения;
- обрыв и восстановление сети (выключить/включить Wi-Fi) не порождают ложных сигналов ни у переподключающегося, ни у остальных;
- существующие сценарии звонка (мьют, шаринг экрана, качество сигнала) не деградировали; `npm run test:e2e` проходит целиком.

## Вне области

- Звуки для тех, кто не находится в звонке (Discord-подобное «слышно из канала») — требует трекинга голосового присутствия в основном WS-хабе (VYC-22 не смержен в `main`).
- Отдельная громкость именно для этих сигналов — используется общий `settings.volume`.
- Звук при входе/выходе в P2P-звонке.
